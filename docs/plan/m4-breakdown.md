# M4 breakdown: Party play + 2D combat on map

Status: **Planning draft** · Parent milestone: architecture §11, M4 (wk 12–19) · Source card: `bb863de6` · Party-chat moderation carry-over: `7bbe618b`

## Problem and outcome

M2 proves a solo DM loop; M4 makes that loop work for a party of 2–6 people, with fair shared turns and authoritative combat played directly on the 2D map. Players must be able to coordinate, act, reconnect, and complete map combat without the LLM owning game state or bypassing moderation. M4 is complete when the milestone exit evidence in architecture §11 exists: six-sim-player scripted sessions green, a real 3–4 person playtest including map combat, spotlight measured, and keyboard-only combat passes.

## Scope

**In scope:** collect-then-resolve exploration rounds; accepted-input queueing; timers and host resolve-now; away/autopilot and drop-in/out; host controls; rest votes; spotlight; OOC party chat; end-to-end 2D combat in the Room with movement and area-aim tools, reactions/opportunity attacks, deterministic monster policy, and one narration per DM turn; party and combat UI including keyboard/list/reduced-motion/mobile paths.

**Not an M4 gate:** first-visible, input-judge, or output-gate latency remediation. The three measured M3 latency misses remain misses and move to M5 follow-up cards `62400d89` and `b576951d`; do not weaken or bypass moderation to improve latency. M4 still routes every party chat message through the existing M3 input gate. No new Workboard cards are created by this breakdown.

**Not in scope:** free-flow rounds, spectators, whispers/secret channels, 3D/isometric maps, map uploads, procedural map generation, or changing the M3 moderation policy/thresholds.

## Proposed first slice that ships alone

Ship **moderated OOC party chat** as a standalone vertical slice after work item 0: introduce the typed chat event/message contract, use the existing WebSocket ticket gate and origin check, enforce per-seat rate/flood controls before the judge, re-check current non-revoked seat access on each send/read, and run input moderation before persist or broadcast. Include the ratified length cap, neutral private rejection, non-allow logging, report/X-card/pause/mute handling, 30-day raw-transcript retention and ADR-028 report clocks/legal hold, and a separate chat channel. OOC text must never be included in, quoted by, or echoed in DM prompts or narration. It is independently useful before multi-action round resolution and proves the required party-chat safety path without coupling chat to a DM turn. Chat moderation is deliberately completed before persist/broadcast; unlike DM action input, it does not run in parallel with round close. Its precise blocker is the chat message type identified by card `7bbe618b`; do not start the implementation slice until Sage's contract decision and that type exist.

## Moderation and M3 latency carry-over

- Party chat, action text, edits, and any other player-authored free text must use the M3 input gate **before storage or DM delivery**: deterministic hard floor first, then judge; fail closed per ADR-023; neutral private rejection; no raw rejected text in the log; non-allow `moderation_log` record with existing retention.
- Preserve ADR-022's per-socket promise-chain ordering so moderation does not reorder that player's inputs. For cross-player ordering, use server receipt timestamp as specified by spec §6.2 and the M4 round contract.
- The input gate is not chat-only: action submissions and round edits must remain gated before entering the DM batch. Do not treat OOC as an unmoderated bypass. OOC chat is never included in, quoted by, or echoed in DM prompts or narration; the DM path sees round actions only.
- M3 latency misses are tracked for M5, not reclassified as passes: first-visible narration p95 8,051 ms vs ≤3 s; input judge p95 811 ms vs ≤400 ms; output gate judged-chunk p95 794 ms vs ≤500 ms on the buffered path. The streaming production-chunk path remains unmeasured. These gaps do not change gate order or fail-closed behavior.
