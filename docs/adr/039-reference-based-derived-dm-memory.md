# ADR-039: Reference-based derived DM memory and no stored player quotes

Status: Proposed · Date: 2026-10-30 · Refines ADR-006, ADR-017, ADR-024 (Proposed) and ADR-025 (Accepted) · Workboard: fe153f81 (c691a4a5 unverified; Atlas checking board)

## Context

`scene_summaries` stores generated prose. `registry_entries` stores names, aliases, payload prose and materialized search text; `registry_facts` stores fact strings. Retrieval (`RegistryMemory.retrieve`/`contextFor`) and recap callers place these rows into downstream prompts. Current fallback scans arbitrary event payload keys (`summary`, `description`, `name`, `text`). Account deletion in #419 fences affected sessions and scrubs derived rows; substring replacement is unsafe and cannot identify quoted text reliably.

Canonical events distinguish player input from server-authored outcomes. In particular, `PlayerAction.text` is player-authored and excluded, as is `NarrationCompleted` (generated narration can contain player names or reproduce player wording). Existing generated rows lack reliable provenance and cannot be losslessly converted into references.

## Decision

### Input boundary and deterministic fallback

The summarizer receives only a server-built, versioned projection; no raw payload or free-form string is forwarded. Initial event allowlist (fields after schema validation; identifiers are opaque server ids): `CombatStarted` (`combatId`, `entityIds`/`order`); `InitiativeRolled` (`entityId`, integer `total`); `TurnOpened`/`TurnTimedOut` (`turnId`, `entityId`, deadline/action enum); `TurnResolved` (`turnId`, `entityId`, event ids); `ReactionPromptOpened` (`promptId`, `reactorEntityId`, deadline); `ReactionAnswered` (`promptId`, choice enum); `ReactionDeclined` (`promptId`, cause enum); `CombatEnded` (`combatId`/`encounterId`); `EntityPlaced` (`entityId`, grid coordinates); `LateJoinSpawned` (`seatId`, `entityId`, `sceneId`, grid coordinates, numeric round); `EntityMoved` (`entityId`, grid path, numeric cost); `MoveStarted` (`entityId`, grid path, turn id); `MoveEnded` (`entityId`, turn id, reason enum); `OpportunityTriggered` (`moverId`, `attackerId`); `AreaResolved` (grid cells, entity ids); `HpChanged` (`entityId`, integer delta/hp); `ConditionApplied`/`ConditionRemoved` (`entityId`, condition id); `SlotSpent` (`entityId`, integer level); `ContentTierChanged` (tier enums). `RollEvent` is not allowed because its label/dice fields are free-form; only an explicit future projection of numeric/boolean outcome fields may be added. No event is currently classified as player-authored free text; all listed values are server/engine-generated identifiers, numbers, enums, or coordinates. `SeatJoined` is an existing event (see `Room.ts` near line 2186) whose payload includes `displayName` and `accountId`; it is explicitly excluded from summarizer input, as are `PlayerAction.text`, `NarrationCompleted`, chat, tool arguments, registry strings, notes, labels, and unknown types/fields. There is no `CharacterJoined` event in this contract. Display identity and account handles are used only by server-side screening and are never sent to the summarizer/model, including as prompt context. For every projected field, validation rejects values not matching its declared primitive/domain type; every opaque-id field must parse as the exact server-issued identifier type/format, resolve in its authoritative table within the session, and pass the relevant seat/character binding check. Reject unknown, malformed, cross-session, or unresolved ids; never coerce free-form strings into ids. `ConditionApplied.source` is an unconstrained free string and is excluded from the allowlist (only its validated `entityId` and `conditionId` may be projected). The allowlisted projection is the sole input to both model and deterministic fallback; fallback formats enumerated structured fields only. Any type/field addition requires privacy review and versioned allowlist update.

### References, mapping and write gate

Persist opaque character-reference tokens instead of player-character display names or aliases in every derived summary/registry field, including registry name, aliases, payload, facts, search document/vector source and any derived cache. Tokens are generated with a cryptographically secure RNG (at least 128 bits of entropy), are not derived from ids/names, and are stable per character per session—not per summary—so references link consistently across summaries and registry rows. Migration `0045_derived_memory_character_refs.sql` creates `session_character_tokens(session_id uuid REFERENCES sessions ON DELETE CASCADE, character_id uuid, token text, PRIMARY KEY(session_id,character_id), UNIQUE(session_id,token), CHECK token format/length)` and `derived_memory_character_refs(session_id uuid REFERENCES sessions ON DELETE CASCADE, character_id uuid, row_kind text CHECK IN ('scene_summary','registry_entry'), row_id bigint, PRIMARY KEY(session_id,character_id,row_kind,row_id))`. These types match the referenced schema: `sessions.id` is uuid, `account_characters.id` (character_id) is uuid, and both `scene_summaries.id` and `registry_entries.id` are bigserial/bigint in migration `0014_registry.sql`.`, plus indexes `(session_id,character_id)` and `(session_id,row_kind,row_id)`. The second table is the required token-to-row deletion index: each summary/registry version records every referenced character token; for registry entries deleting the parent cascades to `registry_facts`. Writes update derived row and reference index in the same transaction. Deletion first selects indexed row ids for `(session_id,character_id)`, deletes those summaries/registry versions and their facts, then deletes mapping and index rows; session cascade remains the final cleanup. Mapping uniqueness prevents token collision and row references make deletion independent of text search. For every projected event, validate each referenced seat against the authoritative seat-to-character binding at that event/turn, then require the character id to exist in the captured mapping; never infer a character from a display name. Reject inconsistent, missing, or ambiguous bindings rather than assigning a token. Seat rebinding never retargets an existing character id/token. A new character gets a new token.

At summarizer start, capture the current session lease/fence epoch and authoritative identity inventory: display name, account handle, every whitespace/punctuation-delimited name component, trusted nicknames, and aliases. Screen every component of at least 2 Unicode code points (single-code-point components are also screened as exact tokens); do not only screen the full display name. Normalize both candidate text and needles with Unicode NFKC plus locale-independent case folding; compare whole Unicode letter/number boundaries and common possessive suffixes (`'s`, `’s`, plural possessive `'`, `’`). Nicknames must come from the same trusted profile/alias inventory, not model inference. Validate every generated reference token against the captured mapping and validate token syntax/length. Before any write, reject the entire summary/registry diff if it contains any captured identity variant as a whole word under those rules, or any unknown/malformed token. This applies to every name, including common-word names. A player character may appear in persisted derived memory only as a validated reference token; any literal occurrence of a session player name or alias is ambiguous and rejected. Apply token boundary-safe matching. Apply this gate to model output, deterministic fallback, and any summary/registry write path; do not rely on deletion-time string matching. Registry diffs remain schema validated. On rejection, use a non-identifying static fallback only if it independently passes the same checks; otherwise do not write.

### Name collisions, retry and deterministic fallback

Every session player's display name and alias is screened as a whole word with case-insensitive normalized matching, including names that are common English words. Any literal occurrence is ambiguous and rejected; identity references in persisted derived memory must be validated tokens only. Thus ordinary prose containing a common-word name (for example, “I will…” for a character named Will) also triggers rejection. Accept this false-positive cost to preserve the no-player-name persistence invariant.

On any such rejection, retry summarization once with a stricter instruction to use the character's reference token and avoid the bare word where possible. If the retry is also rejected, discard model output and use the deterministic allowlisted-projection summary, whose formatter omits display-identity fields and emits player references only as opaque tokens; it cannot contain player text. This retry/fallback behavior applies to summary and registry-diff generation. The write path must never fail scene close or block play because of a collision; record a collision metric/log event without including the name or other identifying text. Normalization, component splitting, possessive matching, and Unicode-boundary behavior are normative above; tests include composed/decomposed accents, compatibility characters, and case-fold expansions.

### Read boundary and injection

Stored values are untrusted. Re-screen each retrieved summary and registry value against the current session's character names and aliases immediately before prompt insertion, in both `retrieve` and `contextFor` (including `mentionedFacts`/recap paths that can reach prompts). Drop a row/fact that fails screening; do not repair it with substitution. Resolve token references only after screening and authorization. Bound display names at the renderer (maximum 80 Unicode code points and 320 UTF-8 bytes; reject/neutral-label longer values), and escape them for the exact prompt/rendering context. Rendering is single-pass: parse the stored template once, substitute tokens from the captured mapping once, and never rescan or substitute inside inserted names. A character name containing a token-shaped string is emitted literally and cannot trigger a second replacement. Deleted/unavailable references render a neutral label.

### Transaction fencing, holds, deletion and legacy clear

`RegistryMemory.closeScene` writes through `this.pool`; its transaction must lock/check the session lease row and compare the fence epoch captured when summarization began before inserting the summary or registry diffs. A changed epoch, active deletion fence, or post-scrub state rejects the whole write (rollback); checking only at summarizer start is insufficient. Apply equivalent write fencing to other registry mutation entry points.

Legal holds are an exception to deletion approved by the owner (Chris) on 2026-10-30; see Owner approvals below. The intended hold-detection source is the existing `legal_holds` table defined in `apps/server/migrations/0006_retention.sql` (session holds match `kind='session'` and `item_id=session_id::text`). A held session's derived rows, token map, and token-to-row index are retained unchanged, even after a deletion request. Hold detection must occur before any mutation and fail closed for the entire affected session; no partial scrub. Reply to a deletion request by confirming the request is recorded but that specified held data cannot be erased while the hold applies, identifying the hold basis/process without disclosing another party's data, and offer no claim that deletion is complete. Only an authorized owner/legal-hold release permits later deletion. The legacy clear also skips held sessions and cannot bypass hold checks through bulk migration.

Code inspection: `registry_entries` are written from validated registry events and scene-close diffs; no replay/rebuild path reconstructs them from canonical events. Therefore a one-time legacy clear loses registry continuity (and legacy summaries) and cannot promise reconstruction. Make the one-time clear an implementation gate requiring explicit owner (Chris) approval before execution. Owner decision (Chris), recorded 2026-10-31 after the continuity-loss correction: the one-time clear of legacy rows is approved as a separate gated job (see Owner approvals below). Until that job runs, legacy rows persist and may retain player names/quoted text, and rollout must not claim the invariant for pre-existing rows; new writes still enforce it. Clear only unheld sessions, with idempotent counts-only audit. Do not attempt string replacement or heuristic classification.

### Migration, deployment, rollback and operational retention

Migration 0045 is additive and transactional: create the two tables and indexes above; do not rewrite/drop legacy rows and do not backfill mappings by text matching. Deploy order: (1) apply 0045; (2) deploy code that dual-writes token mappings and `derived_memory_character_refs` while reads/deletion tolerate absent reference rows; (3) enable the new summarizer/write/read gates behind the rollout flag; (4) verify reference-index coverage and zero gate-bypass metrics; (5) only then enable indexed deletion. A resumable reconciliation job processes rows in bounded batches with checkpoint `(session_id,row_kind,row_id)`, idempotent upserts and per-batch transactions; interruption leaves already indexed rows valid and remaining rows explicitly unindexed, and deletion for an affected character fails closed (session-scoped conservative derived-row purge after hold check, or defer and report incomplete) rather than silently claiming success. It must not infer references from substring scans.

Rollback: turn off gated writes and revert application code first; the additive tables remain unused and can be dropped only after confirming no deployed reader/writer depends on them and after preserving required deletion/audit state. Do not rollback by restoring legacy writes or deleting newly generated rows. If migration is partially applied, rerun idempotently; if indexing is partial, keep indexed deletion disabled and use the fail-closed fallback.

Provider and observability retention: the summarizer/model prompt never carries display identity or account handles; this is the same rule as the input boundary above. Resolve identity locally through validated opaque references after model generation, not through prompt identity. Configure the selected provider endpoint for zero-data-retention/no-training where supported; if an endpoint's retention, training, or request logging policy is unknown or incompatible, do not send summarizer content to it. Provider-side retention cannot be revoked by local deletion, and the product must disclose that boundary. Disable body capture in application/provider request and response logs, traces, error reports, and support dumps; redact names and rejected model output before recording. Cost records may retain provider, model, timestamp, token counts and cost only, never prompt/response/name text. Backups, WAL archives, and replicas retain deleted rows until their documented maximum expiry; deletion response must state that bounded window, and purge/restore procedures must reapply deletion tombstones before serving restored data.

## Export and rewind

`accounts/export.ts` currently exports solo-session summaries, but not registry entries or reference mappings. Keep summary export behavior, ensuring exported summaries are screened and rendered only for the exporting authorized character/session; never export token mappings or another player's names. Document this scope and apply the same deletion/hold lifecycle to any future export of derived rows.

Honor ADR-024/025 turn linkage: scene summaries and registry versions carry the producing `turn_id`; a rewind removes rows from reverted turns and restores surviving supersession links atomically with `TurnReverted`. Token mappings are character/session identity data, not turn-derived data, and are not removed by rewind. Rewind must not make a token available for a different character. Legacy NULL `turn_id` rows retain the ADR-024 limitation until the approved legacy clear; ADR-025 linkage does not weaken the new write gate.

### Options considered

| Option | Cost and trade-off |
|---|---|
| **A. Reference-bearing prose (chosen).** | Medium-high. Preserves cross-summary continuity while enforcing the write/read boundaries above; legacy clear entails explicit continuity loss and approval gate. |
| **B. Fully structured memory records.** | Higher redesign cost; stronger typed references, but changes all persistence, retrieval, recap, search and presentation callers. |
| Name-removal/string scrub | Rejected: ambiguous, corrupts common/co-player text and cannot reliably detect paraphrases or quotes. |

## Consequences

- Deletion operates on character ids/references and removes mapping rows and affected derived data transactionally; no name-based scrub. Search indexes are regenerated from screened reference-bearing fields.
- Rename changes rendering only. Seat rebinding does not retarget historical references. Deleted refs are neutralized, never rendered with former names.
- NPC/location names remain canonical; the guarantee is specific to player characters and player-authored text.
- Search may expand authorized query terms at read time, but never persist current player names. Reduced recall is acceptable over persisting names.
- Recap/cache consumers must use the same screening, authorization and single-pass rendering seam.
- Workboard card `c691a4a5` is unverified; Atlas is checking the board. The stored-injection requirement is included regardless.

2. **Prism — L (8–13 days): transactional persistence and read/render seam.** Fence-checked closeScene and all registry writers; retrieval/contextFor/recap screening; authorized token resolution; bounded escaped names and single-pass renderer; search refresh and cache invalidation.
3. **Forge — M (5–8 days): deletion, holds, rewind/export and approved rollout.** Hold-aware fail-closed scrub and legacy clear; mapping lifecycle; ADR-024/025 turn linkage; solo export screening; counts-only clear job gated on explicit Chris approval and documented continuity loss.
4. **Prism — M (5–8 days): verification and regression review.** Cover forbidden event/text fields, case-insensitive whole-word name/alias rejection including common-word names, retry/fallback/metrics, malformed/unknown tokens, cross-summary linking, injection on retrieval, token-looking display names, stale fence/post-scrub writes, holds, rewind, export, deletion, and legacy-clear approval gate.

## Verification plan

- Projection tests assert only named allowlisted fields reach both model and deterministic fallback; `SeatJoined` (including `displayName`/`accountId`), `ConditionApplied.source`, `PlayerAction.text`, and `NarrationCompleted` never do. Assert the model prompt and deterministic fallback contain no display identity/account handle, and that identity resolution is local through validated tokens.
- Acceptance tests seed a distinctive quoted player utterance in `PlayerAction.text`; force the model to return the quote in `summary`, in each registry string field (`name`, `aliases`, `role`, `facts`, `note`, `topic`, `ruling`), then exercise first rejection, retry, second rejection, deterministic fallback, and assert the quote is absent from persisted `scene_summaries`, `registry_entries` (including `name`, `aliases`, `payload`, `search_document`), and `registry_facts`. Separately call every registry write entry point (`upsert`, `upsertMany`, scene-close diffs, event persistence) with quoted text and assert transaction rollback/no row. Assert model retry and fallback cannot bypass the same gate; inspect DB state after each path. These are required implementation acceptance tests, not claimed as run in this ADR-only change.
- Write tests reject each identity variant in every summary/registry field (component, account handle, alias, nickname, possessive, NFC/NFD/NFKC spelling and case-fold equivalent) and reject malformed/unknown tokens; validation tests reject malformed, unresolved, cross-session, or incorrectly typed opaque ids and prove `ConditionApplied.source` is never projected; assert stable cross-summary token identity and per-event mapping correctness.
- Transaction tests race closeScene with #419 fencing and prove stale epochs/post-scrub writes roll back. If Chris approves the proposed legal-hold exception, tests prove held sessions are unchanged and deletion fails closed.
- Retrieval tests prove stored injection/name leakage is dropped before prompt insertion, rendering bounds/escapes names, and token-shaped names are not rescanned.
- Rewind tests prove turn-linked rows are removed atomically and mappings remain character-stable; export tests enforce solo authorized scope and omit mapping data.
- Migration tests apply 0045 to a database with existing rows, validate indexes/uniqueness/FKs and prove legacy rows remain untouched. Test deploy compatibility with old code, interruption/restart during index reconciliation, rollback with additive schema retained, and that indexed deletion finds summary and registry rows plus cascading facts without substring search.
- Legacy-clear tests establish hold-awareness, idempotence, and no registry rebuild claim. Execution remains blocked until explicit Chris approval. Hold-deletion tests verify held rows/mappings/indexes remain, response reports deletion incomplete due to hold, then deletion completes only after hold release. Provider/logging tests assert request/response bodies are absent from logs/traces/cost records; verify configured retention/ZDR policy before identity-bearing requests.
