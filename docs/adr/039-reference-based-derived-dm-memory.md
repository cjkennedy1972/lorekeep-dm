# ADR-039: Reference-based derived DM memory and no stored player quotes

Status: Proposed · Date: 2026-10-30 · Refines ADR-006, ADR-017, ADR-024 and ADR-025 · Workboard: fe153f81 (also check c691a4a5)

## Context

`scene_summaries` stores free-form generated prose. `registry_entries` stores names, aliases, payload prose and a materialized `search_document`; `registry_facts` stores free-form fact strings. `RegistryMemory.retrieve` searches those stored strings, and `loadRecapMemory` supplies scene summaries to durable recap callers. `summarizeScene` sends canonicalized event payloads to an LLM and stores its prose/diffs; its deterministic fallback copies `summary`, `description`, `name` or `text` fields from events. Thus a player character's display name can be copied into multiple derived fields, and player-authored text can influence persistent memory or be reproduced verbatim. String-matching deletion is not a safe substitute: it can corrupt co-player text or common words, and matching cannot reliably identify quoted text. PR #419 (55aab34c) is an interim mitigation: deletion clears derived rows for affected sessions rather than attempting to scrub strings.

The tables are regenerable, but do not currently preserve structured references to player seats/characters. Character ids and seat ids are available in canonical game state/events, but a scene summary is plain text. Existing generated rows cannot be losslessly converted into references; matching names in legacy text would recreate the rejected unsafe approach.

## Decision

Persist summaries and registry prose with explicit, opaque character-reference placeholders rather than player-character display names. The summarizer receives a server-built character map (stable seat id and character id paired with an opaque placeholder), and is instructed and schema-validated to emit placeholders for those characters. Placeholders are retained through scene summary, registry names/aliases/payload/facts, and regenerated `search_document`. The placeholder-to-current-display-name mapping is resolved only when presenting text to a player or composing a player-facing prompt. Internal storage and deletion logic operate on references, never rendered names. On character/account deletion, invalidate or anonymize references by id; unresolved/deleted references render as a neutral label (for example, “a former party member”), never the former name. A seat binding change must not silently retarget old references to a new character.

The summarizer input is a server-authored allowlist/projection of events. Exclude raw player submission text and any free-text field whose origin is player-controlled; do not ask the model to quote, preserve, or summarize player-authored wording. It may retain bounded facts derived from validated game events, but outputs remain untrusted data and continue through existing validation/moderation. Deterministic fallback uses the same allowlisted projection and placeholder rules; it must not copy arbitrary `text` fields. This makes the persistent memory a record of game state, not a transcript of player-authored input.

### Options considered

| Option | Migration cost | Recap/search impact | LLM prompt impact |
|---|---|---|---|
| **A. Reference placeholders in generated memory (chosen).** Provide opaque character refs to summarizer; persist refs in all derived text fields; render names at read time. | Medium-high: alter event projection, summarizer contract/validation, storage/rendering callers, search materialization, deletion and export; legacy rows cannot be converted safely, so clear legacy derived memory once (or retain only rows provably free of player identity/text, which requires a defensible provenance test). No per-word name matching. | Search indexes placeholders instead of current display names; expand query with current names/aliases at retrieval or resolve references for lexical matching without persisting them. Recap input resolves names for the current audience after deletion checks. Deleted refs remain anonymous and no longer match their former names. | Adds stable opaque reference tokens and a rule to use them exactly; raw player text is excluded. Validate every emitted token against the supplied map; unknown/malformed tokens reject the summary/diff or replace it with safe fallback. Slight token overhead. |
| **B. Structured memory records with seat/character ids, render complete prose at read time.** Store semantic clauses plus typed subject/participant references; no names in persisted memory. | High: redesign summary and registry persistence/read APIs, backfill impossible for free prose, rewrite search indexing/ranking and all presentation paths. More robust than tokenized prose if representation is truly structured, but much larger model change. | Best control over personalized recap and search, but every consumer must render; retrieval must query structured text and current names consistently. Significant risk of a reader bypassing the renderer. | Model emits a larger structured schema with typed references; more validation and potential fallback when outputs are incomplete. Easier to verify authorship/reference membership than arbitrary prose. |

A plain “prompt the model to replace names with placeholders” without persisting/verifying references is not accepted: it permits omissions, invented tokens, or names embedded in paraphrase. Option A therefore requires exact placeholder validation and read-time rendering as one interface, not a prompt-only convention.

### Consequences

- Deletion becomes a reference operation. Identify all memory rows through structured character/seat references and either remove the affected reference-bearing memory or retain its non-identifying remainder with a deleted-reference marker. The deletion transaction must also rebuild/remove corresponding `search_document` and search vectors; no display-name scrub is used.
- A character that is renamed changes only the read-time rendering. A former/deleted character is never rendered by their deleted name. Rebinding a seat does not change historical references.
- Registry entities that are NPCs/locations retain their own canonical names; the privacy guarantee applies to player characters and player-authored text, not every coincidentally equal string. To avoid ambiguous common-word scrubs, only typed references trigger anonymization.
- Search must include current authorized display names as query terms or join references for ranking, without writing those names to durable search text. If that cannot be done safely in the first implementation, accept reduced search recall for player-character-name queries rather than persist names.
- Recap generation receives rendered, authorized memory only after reference resolution; snapshots/caches that embed a rendered name must be invalidated/rebuilt when deletion or character binding changes. This ADR does not authorize retaining the old name in a recap cache.
- Legacy unprovenanced text cannot be migrated safely. Clear legacy `scene_summaries`, registry versions/facts and materialized search fields during rollout; summaries and registry can repopulate through normal play. This intentionally trades historical continuity for a deterministic privacy boundary. Do not attempt regex/string replacement.
- This design does not change canonical event/snapshot retention or quote handling in message reports (ADR-017); it prevents raw player text from being copied into this derived-memory class.

## Implementation breakdown (proposed)

1. **Forge — L: placeholder and provenance contract.** Build a server-only map from stable seat/character ids to per-summary opaque tokens; project only safe event fields and omit raw player submissions; update LLM schema/prompt, validate tokens and deterministic fallback. Ensure a binding change never retargets old tokens.
2. **Prism — L: persistence, render and search.** Persist reference-bearing summary/registry data; update `search_document` construction, retrieval, recap and every player-facing memory reader to resolve currently authorized names. Invalidate recap caches on identity/deletion changes. Keep authorization checks in the shared read seam.
3. **Forge — M: deletion and legacy rollout.** Extend account/reusable-character deletion to invalidate/anonymize references and search materializations transactionally; add a one-time legacy derived-memory reset migration/job with idempotent progress and counts-only audit. Preserve PR #419 fallback behavior until rollout is complete.
4. **Prism — M: tests and regression review.** Exercise deleted and renamed characters, two players with overlapping/common-word names, seat rebinding, unknown tokens, a malicious player quote, deterministic fallback, search by current name, recaps/cache invalidation, export, deletion rollback and legacy cleanup. Assert no deleted display name or raw player quote remains in `scene_summaries`, registry fields/facts, `search_document`/search vectors, or derived recap caches after deletion.

## Verification plan

- Unit tests: safe-event projection excludes submitted text; token validator accepts only references supplied by the server; malformed/unknown refs trigger a non-identifying fallback; deterministic fallback follows identical rules.
- Database tests: persisted summary/facts/search document contain placeholders/ids but not player display names or submitted strings; read-time rendering returns the current name before deletion and neutral text after deletion; deletion removes/anonymizes references and refreshes all materialized search fields atomically; rollback preserves a consistent pre-delete state.
- Integration tests: retrieve and recap with current/deleted names; verify cache invalidation and no old name leakage; verify a changed seat binding cannot reveal/retarget history; verify raw prompt-injection text never appears in durable derived memory.
- Migration test: legacy derived data is cleared without rewriting canonical events/snapshots; repeated rollout cleanup is safe. Do not claim legacy text can be safely classified by substring.
