# ADR-041: Two-phase seat resume credentials

Status: Proposed · Date: 2026-10-31 · Owner: Chris Kennedy · Work item: seat-credential residual

Append-only: this ADR supersedes the process-local unresolved-invalidation fence as the safety mechanism for failed credential delivery. It does not change the seat ownership, host-approval, or solo-owner-recovery policies in ADR-031, ADR-036, and ADR-037.

## Context

A seat resume token is a random 128-bit bearer credential. The server stores its SHA-256 hash in `seat_resume_tokens.token_hash`. The socket lease (`active_socket_id`, `heartbeat_at`) serializes the controlling socket and considers a socket live for 15 seconds, as established by PR #436. The current `ws.ts` path commits a new token hash before sending `SeatAuthenticated`. If send reports failure, it tries rollback and invalidation writes. Consecutive database failures can leave a token hash valid even though the player may never have received that token.

PR #441 improved ordinary rollback and PR #444 added invalidation retries and an in-process fence. The fence protects only its server process and disappears on restart. Another gateway sharing the database can accept the credential after lease expiry. Persisting a separate invalidation marker in the same unavailable database does not solve this ordering defect.

The invariant is: **only a durably activated credential authenticates; a pending candidate never authenticates on any process or after restart.** A send error is ambiguous: it does not prove that zero bytes reached the client.

## Decision

Use a database-backed two-phase rotation. Leave the current active hash unchanged while a candidate is pending. Send the candidate only over a transport verified as TLS, have the client durably store it before sending its receipt ACK, then promote it with one compare-and-swap (CAS). The same activation CAS replaces the active hash and records durable ACK-idempotency data. No rollback or invalidation write is needed to make an undelivered candidate safe: pending candidates categorically do not authenticate.

The client durably stages each candidate keyed by rotation id and reads it back to verify persistence before sending `SeatResumeTokenReceived(rotationId)`. A persistence error or read-back mismatch means no ACK is sent; keep the active token and retry persistence/receipt before the pending expiry. Keep the active token and staged candidates until `SeatResumeTokenActivated(rotationId)` arrives; on confirmation, promote the matching candidate only if its local receive sequence is not older than the latest already-promoted sequence; never let a delayed confirmation roll the active pointer backward. Retire candidates at or before the promoted sequence, while preserving later candidates. If a later `SeatAuthenticated` arrives after a takeover, persist it under its own rotation id and local receive sequence, and make it the latest fallback candidate; retain the active token until an applicable confirmation. Retain only the latest N staged candidates, and purge any candidate after its pending deadline plus a bounded local cleanup margin; never purge the active token on that basis. On reconnect, send exactly one `ResumeSeat` frame per WebSocket upgrade containing an ordered list of at most two tokens: `[active, latestCandidate]`. If that reconnect authenticates using the staged candidate, the client promotes that candidate as active and retires the old active token using the same sequence-ordering rule as activation confirmation; no `SeatResumeTokenActivated` arrives on this path. The server reads the active hash once and performs the same fixed-path comparisons for both supplied tokens; pending fields are never authentication inputs. Whether the submitted credential is unknown, pending, or expired, an unauthenticated presenter receives the identical uniform invalid-credential response, close behavior, and timing-equivalent handling. If neither matches, return that response. The existing limiter charges one attempt at WebSocket upgrade, so both token checks in this single `ResumeSeat` frame consume exactly one of the five allowed seat-auth attempts per seat per 60 seconds. If both supplied credentials are invalid because the candidate and activation confirmation were lost, show an explicit “needs host approval” recovery state to the owner and request the existing host-approved flow rather than silently retrying. The owner-visible host-approval claim request is the recovery signal; do not hide this state behind repeated reconnect attempts. Never log candidate plaintext or hashes.

Rotation ids are server-generated UUIDv4 values from the application CSPRNG (`crypto.randomUUID`, `crypto.randomBytes`, or an equivalent cryptographic generator). Candidate tokens also come from the application CSPRNG. The existing `md5(random()::text ...)` pattern is forbidden for any security-relevant id or credential. The server-side socket id is unique per connection, never reused, and never sent to clients. ACKs are accepted only on the currently open WebSocket that received the candidate; socket identity is derived server-side, not supplied by the client. Unknown-rotation, wrong-socket, expired, and otherwise rejected ACKs have the same externally observable response so they do not form an oracle. **Credential-response rule:** unauthenticated and invalid-token presenters receive the same invalid-credential response, close behavior, payload, and timing-equivalent comparison path whether a submitted candidate is unknown, pending, or expired. The server reads only the active hash for authentication; it never queries pending state to decide an unauthenticated response. Pending-rotation, cap-exhausted, activation-committed, abort, and deferral details are disclosed only on an already authenticated socket. Deferral/abort signals go only to the current authenticated lease holder and the host audit channel, never to an invalid or stale presenter.

**Clock rule:** all lease, pending-expiry, rate-window, and audit-time comparisons and values use PostgreSQL `clock_timestamp()`, including after advisory-lock waits; transaction-start timestamps are never used. New schema columns must not use transaction-time clock defaults. `SeatTakenOver.at` must use the DB-clock timestamp returned by the lease/takeover write, not an application clock.

**Transport rule:** do not emit `SeatAuthenticated` or a candidate unless the server verifies a TLS connection. Direct TLS is accepted. Behind a proxy, accept TLS only when the peer address is in a configured trusted-proxy list and that proxy attests `X-Forwarded-Proto: https`; ignore that header from untrusted peers. A loopback/development exception is available only behind an explicit configuration flag, OFF in production. Serialization/logging middleware must redact candidates and hashes, not merely rely on call sites to omit them.

Rotation is an effective revocation of the old token **at activation**: unlike a design that retains the old hash after activation, the old hash is immediately replaced, and no prior-token slot remains. A stolen old token remains usable during the pending phase, but stops authenticating as soon as activation commits. Rotation does not revoke a stolen token before activation; seat revocation or session deletion remains the emergency revocation mechanism.

### Exact row state machine

One row remains keyed by `(session_id, seat_id)`. `token_hash` is the only authenticating credential hash. Pending values and last-activation metadata never authenticate. `rotation_window_started_at` is the single authoritative rate-window anchor; no second pending-window anchor is stored.

| State | Row predicate | Authentication |
|---|---|---|
| `ACTIVE` | No pending tuple; `token_hash` is current | Active hash only |
| `PENDING` | Pending hash/id/socket/expiry/start-time tuple is set and expiry is in the future | Active hash only; pending hash is always rejected. Pending metadata never blocks authentication with a valid active credential. |
| `PENDING_EXPIRED` | Pending tuple exists but `pending_expires_at <= clock_timestamp()` | Active hash only; expiry itself never blocks valid authentication; cleanup is opportunistic. |

Transitions (all stated writes are in the same transaction as their authorization/lease decisions):

1. **Authorize, take over if needed, begin rotation:** `authorizeSeatSocket` takes the existing transaction/advisory lock and applies the live-lease-first policy. The lease is the only cross-socket controller exclusion. Pending metadata is never a reason to refuse a valid active-token reconnect, host-approved claim, or eligible solo-owner recovery. When an authorized new socket obtains the seat after the prior lease is expired or no longer owned, abort any other socket's pending tuple by CAS over the exact `(pending_rotation_id, pending_token_hash, pending_socket_id)` and lease ownership, then reserve the new socket. A valid active token on a live current socket cannot start a concurrent second rotation; its existing socket may retry after its pending tuple expires or is aborted. Host-approved and solo-owner eligibility checks remain unchanged. These owner-authorized paths bypass both the cap and its counter and receive a fresh candidate; they are never admitted without the credential needed to complete recovery.

   For a permitted start, generate candidate `Tn` and rotation id `Rn`. In the same transaction, CAS-set `pending_token_hash=sha256(Tn)`, `pending_rotation_id=Rn`, `pending_socket_id=serverSocketId`, `pending_expires_at=clock_timestamp()+interval '30 seconds'`, and `pending_started_at=clock_timestamp()`, leaving `token_hash` unchanged. The per-seat cap is six non-activated starts in each anchored 60-second window. Update the counter in the SAME CAS/transaction that begins the pending rotation; a failed pending-row write does not count. Successful activation refunds that ordinary start in the activation CAS only when `pending_started_at >= rotation_window_started_at` and `clock_timestamp() < rotation_window_started_at + interval '60 seconds'`; if that refund takes the count to zero, clear both count and anchor in that CAS. Aborted, expired, and otherwise non-activated ordinary starts remain counted; when the window elapses, reset the counter before the next ordinary start. Successful rotations do not consume the failure budget.

   The cap applies only to ordinary token-based starts. Owner-authorized host-approved claims and eligible solo-owner recoveries bypass both the cap and its counter, remain admitted, and receive the normal fresh candidate through pending → ACK → activation. No path may create more than one pending tuple per seat. A host-approved or solo-owner recovery at the cap therefore completes normally without requiring another approval at the next reconnect after activation. The cap does not block a valid active-token authentication: when an ordinary rotation is deferred, tell only that authenticated holder; never disclose cap state to an invalid presenter. Host-visible `SeatRotationDeferred` and `SeatRotationAborted` audit events and the existing `SeatTakenOver` event record seat id, actor account id when known, and a keyed hash of client IP for attribution; never include token, credential hash, or socket id. Deliver through the host audit/notification channel and coalesce repeated events per seat/time window to avoid alert flooding. Send deferral/abort notices to the current authenticated lease holder when one exists.

2. **Send candidate:** after pending CAS commits, send `SeatAuthenticated(Tn,Rn)` over a verified TLS transport. On send failure or connection close, best-effort clear pending fields by CAS matching the exact pending tuple and socket. If that write fails, expiry and an authorized lease-expired takeover are authoritative cleanup. The candidate remains non-authenticating regardless of cleanup outcome. A live socket with no ACK cannot start a second pending rotation; after expiry it may retry, and that ordinary non-activated start counts toward the cap. An unresolved committed-but-unsent pending tuple only prevents another pending start while the current lease is live; it never blocks valid active-token authentication. A takeover/recovery authorized by host approval or solo-owner policy bypasses the cap.

3. **Client receipt ACK:** the client must first durably persist `Tn` associated with `Rn`, then send `SeatResumeTokenReceived(Rn)`. First check the durable duplicate-ACK case in step 5. Otherwise accept only if the pending tuple, deadline, current open server-side socket identity, and live lease all match. ACK is not an authentication credential. If the pending tuple expired or was aborted/replaced after a lease-expired takeover, reject with the uniform ACK-rejection response. The client keeps both credentials until activation confirmation.

4. **Activate:** in one transaction/CAS, verify the exact pending tuple, unexpired deadline, and lease ownership; replace `token_hash` with `pending_token_hash`; set `rotated_at`; set `last_activated_rotation_id=Rn`, `last_activated_socket_id=serverSocketId`, and `last_activated_at=clock_timestamp()` in this SAME CAS; update/refund the rate counter as described in step 1; then clear all pending fields. The old token becomes invalid at this commit. If the database reports an error with an unknown commit outcome, do not roll back or start another rotation: treat activation as unknown and let the client retry its ACK on the same still-open socket. If the CAS committed, durable idempotency data allows confirmation to be re-sent; if it did not, the still-pending tuple can be retried while valid. Send `SeatResumeTokenActivated(Rn)` only after a confirmed commit or a successful duplicate-ACK lookup.

5. **Duplicate ACK:** on the currently open connection, a duplicate ACK matching the last activated rotation id and recorded server-side socket id, on the same seat, only while `last_activated_at` is within the bounded 30-second idempotency window, AND while that socket still owns the live lease, re-sends `SeatResumeTokenActivated(Rn)` without changing row state. The server socket id is never sent to the client and is unique and never reused. This is not an authentication window: the old token stopped authenticating at activation. An ACK after the deadline, for another rotation, from another socket, or from a socket whose lease expired receives the same response as any other rejected ACK. The client can reconnect using its persisted candidate.

6. **Expiry, abort, and recovery:** pending expires after 30 seconds. A periodic bounded sweeper clears expired pending tuples; correctness does not depend on prompt sweeping because auth rejects pending hashes and checks expiry synchronously. A takeover after lease expiry clears the old pending tuple in its authorization transaction. Emit `SeatRotationAborted` to the current authenticated lease holder where applicable and to host audit, with the defined non-secret attribution only. An expired candidate cannot be activated. The client discards it only after a definitive rejection/expiry response; if uncertain, its single `ResumeSeat` frame is safe because only the active hash authenticates.

7. **Revocation/session deletion:** existing row deletion cascades remain authoritative and remove active, pending, rate, and last-activation metadata together.

All credential transitions use CAS predicates over expected rotation id/hash, server-side socket owner, and lease state; activation and ACK require an unexpired pending deadline. The authorization lock remains keyed by `(session_id, seat_id)` and is taken before row decisions. Expiry sweeps use bounded batches with `FOR UPDATE SKIP LOCKED`; they clear pending metadata only and never promote a credential.

### Schema and mixed-fleet guard migrations

Use two ordered migrations. Assign each its actual next-free number at implementation time (`0049` or later; do not hard-code a number in design artifacts).

1. **Additive schema migration:** add nullable `pending_token_hash text`, `pending_rotation_id uuid`, `pending_socket_id uuid`, `pending_expires_at timestamptz`, `pending_started_at timestamptz`, `last_activated_rotation_id uuid`, `last_activated_socket_id uuid`, `last_activated_at timestamptz`, `rotation_window_started_at timestamptz`, and `rotation_starts_in_window smallint NOT NULL DEFAULT 0`. Add checks requiring pending hash/id/socket/expiry/start tuple to be all NULL or all set; last-activated id/socket/time to be all NULL or all set; rate-window start to be NULL exactly when its count is zero; and count between 0 and 6. Add a partial index on `pending_expires_at` where pending hash is non-NULL. No credential backfill is needed: existing `token_hash` rows remain active and new fields start NULL/defaulted. Keep existing PK, revocation trigger, heartbeat-pair check, and 15-second lease semantics.

2. **Protocol-guard migration (separate, after fleet convergence):** add a `BEFORE INSERT OR UPDATE` trigger on `seat_resume_tokens`. For UPDATE, use `IS DISTINCT FROM` to detect NULL-safe changes to `token_hash`, every pending column, and every last-activated column; raise unless `current_setting('app.seat_token_protocol', true) = '2'`. For INSERT, if `NEW.token_hash` or any pending/last-activated column is non-NULL, raise unless the same marker is present. A trigger-function sketch is:

```sql
IF TG_OP = 'INSERT' THEN
  IF (NEW.token_hash IS NOT NULL OR NEW.pending_token_hash IS NOT NULL
      OR NEW.pending_rotation_id IS NOT NULL OR NEW.pending_socket_id IS NOT NULL
      OR NEW.pending_expires_at IS NOT NULL OR NEW.pending_started_at IS NOT NULL
      OR NEW.last_activated_rotation_id IS NOT NULL
      OR NEW.last_activated_socket_id IS NOT NULL OR NEW.last_activated_at IS NOT NULL)
     AND current_setting('app.seat_token_protocol', true) IS DISTINCT FROM '2' THEN
    RAISE EXCEPTION 'seat token protocol marker required';
  END IF;
  RETURN NEW;
END IF;
IF ROW(NEW.token_hash, NEW.pending_token_hash, NEW.pending_rotation_id,
       NEW.pending_socket_id, NEW.pending_expires_at, NEW.pending_started_at,
       NEW.last_activated_rotation_id, NEW.last_activated_socket_id, NEW.last_activated_at)
   IS DISTINCT FROM ROW(OLD.token_hash, OLD.pending_token_hash, OLD.pending_rotation_id,
       OLD.pending_socket_id, OLD.pending_expires_at, OLD.pending_started_at,
       OLD.last_activated_rotation_id, OLD.last_activated_socket_id, OLD.last_activated_at)
   AND current_setting('app.seat_token_protocol', true) IS DISTINCT FROM '2' THEN
  RAISE EXCEPTION 'seat token protocol marker required';
END IF;
RETURN NEW;
```

Credential-write transactions use only `SELECT set_config('app.seat_token_protocol', '2', true)` after beginning an explicit transaction and before every insert/update, including host-approved and solo-owner paths; never use session-level `SET` or `set_config(..., false)`. An autocommit write after setting the transaction-local marker in a separate statement must fail closed. The third argument makes the setting transaction-local. The marker is a **version fence, not authorization**: a DB-role holder able to set the GUC or disable the trigger already has database-level control. DELETE remains unguarded for revocation. Unprotected lease/heartbeat updates continue without the marker. Old binaries cannot set the marker, so protected writes fail closed, including `ON CONFLICT DO UPDATE`. This also means an old binary cannot take over or claim seats after trigger installation: that is an intentional mixed-fleet outage mode, not a supported rolling state. The trigger, not an operator checklist, enforces the boundary. Drop it before any old binary runs during rollback.

A new-binary startup check may additionally refuse to serve seats unless the guard schema is present, but it is defense in depth; it does not replace the trigger. The deployment flag is per-deployment and remains OFF until the trigger is installed.

### Alternatives considered

| Option | Assessment |
|---|---|
| **A. Pending hash, send, ACK, CAS activate (chosen)** | Pending is categorically excluded from authentication. Keeps the old hash active only until activation, then replaces it immediately. Client write-ahead persistence plus same-frame reconnect fallback handles lost confirmation without leaving a stolen old token valid after activation. Shared DB state handles processes and restarts. |
| **B. Persisted invalidation marker** | Rejected as primary fix: marker write uses the same database that failed for rollback/invalidation. An outage can leave the marker absent. |
| **C. Deliver then commit** | A delivered-but-uncommitted credential cannot authenticate, and the old token remains active, but this alone lacks durable in-flight identity, socket ownership, idempotent ACK, and safe reconnect semantics. Pending state plus CAS provides those boundaries. |
| **D. Keep both hashes valid until client ACK** | Rejected: accepting the candidate before durable activation reintroduces early validity, while retaining the previous token after activation lets a thief using that token retake the seat. ACK triggers the activation CAS; only the candidate remains valid after it. |
| **E. Process-local fence or durable fence-only** | Rejected: process-local state is not shared; durable fence-only depends on the same database and cannot establish safety when its write fails. Safety follows from the pending-vs-active credential state. |

## Consequences and code sites

- `apps/server/src/gateway/resumeTokens.ts`: remove the existing `md5(random()::text ...)` reservation id generation (near line 136) and use the application CSPRNG for candidate/rotation ids. Change `authorizeSeatSocket` to reserve a pending candidate without overwriting the active hash; authenticate only against `token_hash`; add begin/activate/abort/sweep and duplicate-ACK operations; update the cap in the same row CAS; use `clock_timestamp()` in every expiry/window/lease operation and set the protocol marker in every credential-write transaction. Keep these rules behind a cohesive rotation interface.
- `apps/server/src/gateway/ws.ts`: replace commit-before-send plus rollback/invalidation retries with pending reservation → verified-TLS `SeatAuthenticated` → client receipt ACK → activation CAS → activation confirmation. Add the single-`ResumeSeat` two-token fallback and uniform invalid-credential/ACK rejection; validate socket identity from the server-side WebSocket. Publish host-visible, coalesced audit events with seat id, account id when known, and keyed client-IP hash; source `SeatTakenOver.at` from the database-clock timestamp returned by the takeover write (replace the current `Date.now()` payload timestamp at `ws.ts` near line 881). Enforce direct/proxy-attested TLS before emitting authentication/candidate messages; redact secrets at serialization/logging middleware.
- Client wire schema and token persistence: stage candidate durably and read it back before ACK; retain active and candidates keyed by rotation id and local receive sequence; retry ACK on the same live socket if activation outcome/confirmation is unknown; on reconnect send one `ResumeSeat([active, latestCandidate?])` frame per upgrade; ignore out-of-order activation confirmations for active-pointer rollback; discard only candidates definitively rejected/expired or superseded by a later promoted sequence. The server socket id is never on the wire.
- Add migration tests and gateway tests in `apps/server/test/db/gateway.test.ts`, plus client protocol tests. Both gateway instances in the shared-DB test must run production authorization/activation code.
- Remove `unresolvedInvalidations`, invalidation retries, and lease-retention special cases once cutover is complete. The #436 lease remains for controller serialization, not credential revocation. Host approval and solo-owner recovery policies remain unchanged. A thief with a stolen token who wins an expired-seat lease and completes activation can take ownership of the seat until host recovery; this is pre-existing ADR-031 takeover behavior, not a new control or a rotation-only starvation effect. If the thief repeatedly wins without activation, that also degrades legitimate-device rotations. Mitigations remain host-visible takeover/deferred/aborted audit events, existing host-approval policy, and seat revocation; this ADR adds no new takeover control.

## Failure modes

“Attacker” means someone presenting a credential without the legitimate device; the table assumes no database compromise, XSS, or stolen account cookie. A send error is ambiguous about whether bytes arrived. Rotation does not revoke the old token while a candidate is pending, but activation replaces the old hash immediately. A thief presenting a stolen token can win the seat after lease expiry and, if the thief receives and activates a candidate, own the seat until host recovery under the pre-existing takeover policy. Without activation, repeated wins can degrade the legitimate device's rotations while the stolen token remains active. Host-visible takeover/deferred/aborted events (seat id, account id when known, keyed client-IP hash) support detection; existing host approval or seat revocation/session deletion is the mitigation. No new takeover control is introduced.

| Failure/crash point | Player sees / recovery | What an attacker can do |
|---|---|---|
| Pending-row CAS fails before send | No candidate; existing active token still works; owner-authorized recovery remains available | Cannot use candidate; active hash remains unchanged |
| Pending-start CAS has unknown commit outcome | Server does not send. If committed, the orphan pending tuple expires after 30 seconds and blocks only another pending start while the lease is live; active-token authentication still works and this non-activated ordinary start counts toward the cap. If not committed, no pending state exists. | No candidate was disclosed; the pending hash cannot authenticate |
| Client durable candidate write fails or read-back mismatches | Client sends no ACK, keeps the active token, retries persistence before expiry; if it cannot persist, pending expires and the owner sees recovery only if credentials are later lost. The ordinary start counts toward the cap. | Candidate cannot authenticate |
| Send fails and pending clear succeeds | No confirmed candidate; reconnect with old token | Candidate never authenticates |
| Send fails and pending clear also fails | Client may or may not have received candidate; reconnect in one frame with old first and candidate second | Pending candidate is rejected on every process/restart; old token remains active until activation |
| Server crashes after pending write, before send | Client has no candidate; old token works after lease expiry; pending expires/sweeps | Candidate cannot authenticate |
| Server crashes during/after send, before ACK | Client may have staged candidate; old token still authenticates; client reconnect sends one `ResumeSeat([old, candidate])` frame | Candidate cannot authenticate while pending; old token remains usable until activation |
| Send succeeds, socket remains live, no ACK | Client retains active token and candidate keyed by rotation id; it sends no second start on that socket before abort/expiry. The ordinary non-activated start counts toward the cap. | Candidate cannot authenticate; only active token works |
| A later `SeatAuthenticated` arrives after takeover while an older candidate is staged | Client stores candidates by rotation id, makes the later one the latest fallback, and retains active token until confirmation. Reconnect sends active plus latest candidate in one frame; a stale ACK is uniformly rejected. | Only the active hash authenticates; stale pending candidate is rejected |
| ACK arrives on a still-open socket after its lease expired | Uniform ACK rejection; stale socket receives no activation/deferral state; reconnect through a new `ResumeSeat` frame. | Cannot activate or learn rotation state from a stale socket |
| ACK arrives after pending expiry, before sweeper | Uniform ACK rejection; client discards candidate after definitive expiry; active token still works; this ordinary non-activated start counts toward cap | Cannot activate expired candidate |
| ACK from wrong socket or unknown/old rotation id | Same uniform rejection as expired/invalid ACK; no state change | Cannot probe whether a rotation id exists or activate another socket's candidate |
| Activation CAS fails before commit | Client already durably staged candidate and retains old; retry ACK while pending/live, or reconnect with one `ResumeSeat([active, latestCandidate])` frame | Candidate cannot authenticate unless activation commits; old remains active |
| Activation DB error with unknown commit outcome | Server does not roll back. Client retries ACK on the same open socket: if committed, last-activation record re-sends confirmation; if not committed and pending still valid, retry attempts activation. If disconnected, client reconnects with one `ResumeSeat([active, latestCandidate])` frame; the server tries each against the active hash only. | If commit happened, candidate is active and old token is invalid; if not, only old token is active. No ambiguous credential is accepted. |
| Activation commits, process crashes before confirmation | Client retained candidate before ACK. Retry on same socket if still open, otherwise send one `ResumeSeat([old, candidate])` frame; old fails uniformly, then activated candidate succeeds. If candidate was lost too, host-approved recovery applies. | Candidate is the sole active token; old token stopped authenticating at the commit. |
| Confirmation send fails after activation | Client keeps both; retries ACK on current socket or reconnects in one frame with active first and latest candidate second. If it lost candidate, host-approved recovery applies. | Old token is immediately invalid; only the activated candidate works |
| Client ACKs, then crashes before persisting candidate | This ordering violates the client protocol. The server's ACK proves only receipt, not durable persistence; on reconnect old token is invalid, so recover through host approval. Client must persist-before-ACK. | Only the newly activated token works; old token is invalid |
| Pending sweeper fails | Pending row remains until later sweep/takeover; synchronous expiry checks still reject candidate and allow active token | No additional credential is accepted |
| Two gateway instances share DB; one crashes/restarts | Both see the same active/pending state and lease; reconnect candidate works only if activation committed | Neither instance authenticates a pending hash; no process-local fence is required |
| Old socket stalls beyond 15s with pending rotation; valid old-token socket reconnects | After lease expiry, valid active token is admitted; transaction aborts stale pending tuple and may begin a new rotation | Aborted candidate stays non-authenticating; stale ACK fails CAS |
| Ordinary rotation cap reached | Valid-token authentication succeeds on the existing token; only the authenticated holder receives a deferred notice. An unauthorized/tokenless presenter sees only the uniform invalid-credential response. Retry rotation after the anchored window. | A thief holding the token may continue to win expired leases and degrade rotations; the host sees attributed audit events and may revoke the seat. |
| Host-approved claim at cap | Claim is admitted and receives a fresh pending candidate, then follows receipt ACK and activation; no re-approval is needed on later reconnects once activated. | Claim still follows existing host-approval policy; candidate is not valid before activation. |
| Eligible solo-owner recovery at cap | Owner is admitted through normal recovery and receives a fresh pending candidate → ACK → activation; no refusal or tokenless dead end. | Recovery eligibility remains the existing solo-owner policy; pending candidate cannot authenticate. |
| Database protocol trigger rejects legacy write | Old binary cannot credential-write or take over/claim seats after guard installation; fleet must be fully upgraded before this migration. | Legacy path cannot change protected credentials once guarded. |
| Host audit event delivery | Host audit channel receives coalesced takeover/deferred/aborted events with seat id, account id when known, and keyed client-IP hash. | Attribution is still imperfect; no new takeover control is claimed. |

## Test plan (failing-first)

1. Prove pending hashes themselves are rejected as credentials in every path; active hash authenticates; an eligible host-approved or solo-owner claim can independently authorize recovery and create its own pending candidate; expired pending never blocks a valid-token reconnect.
2. Inject pending-CAS failure, send callback error/throw, pending cleanup failure, activation failure before commit, and confirmation-send failure. Assert old-token continuity before activation, immediate old-token rejection after activation, pending candidate rejection, and no credential/hash in logs.
3. Restart test: persist pending row, destroy gateway, create a fresh gateway against same DB after lease expiry, prove pending token rejected; cover crash after send/before ACK and activation commit/before confirmation.
4. Two-process test: two independent gateway instances with separate in-memory state race production authorization/activation against one Postgres DB. Exactly one activation wins; stale rotation/socket IDs cannot activate; pending hash never authenticates. Recreate the first instance and repeat.
5. Race sweeper vs ACK, pending replacement, heartbeat expiry, revocation, host approval, and solo-owner recovery. Prove valid old-token reconnect aborts other socket's pending tuple after lease expiry.
6. ACK tests: duplicate ACK after activation re-confirms without a state change on the same open socket; expiry, wrong socket, unknown/old id, and expired duplicate ACK all have indistinguishable rejection; activation commit-outcome-unknown retries idempotently.
7. Client tests prove candidate durable write/read-back precedes ACK; single-frame active-then-candidate fallback; pending candidate rejected then activated candidate accepted; old token rejected immediately at activation; if candidate and confirmation are lost, UI explicitly enters “needs host approval” with no silent retry loop; host-approved/solo-owner recovery at cap returns a candidate.
8. Rate tests: only unactivated ordinary starts consume the six-per-anchored-60-second budget; successful activation refunds the start; abort/expiry consumes it; pending-start counter update is atomic; host-approved and eligible solo-owner claims at cap are admitted with candidates and do not require repeat approval after activation; valid-token authentication is never refused at cap.
9. Reconnect/throttle tests: one `ResumeSeat` frame carrying `[active, candidate]` consumes exactly one of five seat-auth attempts per 60 seconds; active is checked first, candidate is checked only against active hash, and pending candidate is rejected.
10. Oracle tests: unknown, pending, and expired candidates produce identical invalid-credential payload, close behavior, and timing-equivalent comparison path; cap/pending/activation status is emitted only on an authenticated socket.
11. Clock tests assert `clock_timestamp()` for all lease, pending expiry, rate-window, and idempotency comparisons/values; no transaction-start clock/default is used; `SeatTakenOver.at` is sourced from the DB clock.
12. Protocol guard tests: trigger INSERT and NULL-safe UPDATE branches use `IS DISTINCT FROM`; writes without the marker fail; marked writes succeed; unprotected lease/heartbeat updates and DELETE work; `ON CONFLICT DO UPDATE` is guarded; an autocommit write after `set_config(..., true)` in a separate transaction fails closed; no session-level marker is used. Verify host-approved and solo-owner credential writes set the marker.
13. TLS/proxy tests: candidate and `SeatAuthenticated` are refused on plaintext except the explicit loopback/dev flag; trusted proxy TLS attestation works only for configured proxy addresses; untrusted forwarded headers fail; serialization/logging redacts tokens and hashes.
14. Migration tests verify existing rows remain active, columns/checks/indexes exist, additive migration precedes trigger migration, and session deletion/revocation removes all row state.
15. Failure-injection tests cover pending-start CAS unknown outcome (do not send; committed orphan expires and counts), candidate persistence/read-back failure (do not ACK), a later `SeatAuthenticated` replacing the latest-candidate pointer by rotation id, and ACK from a stalled open socket after lease expiry (uniform rejection).

Do not call a helper spy a multi-process test: both gateways must execute production logic against the same database. Run migration/DB suites, typecheck, formatting, and required CI on the implementation PR.

## Rollout and estimate

Docs-only decision; implementation estimate **L** because it spans server persistence/gateway, client token persistence and reconnect logic, two migrations, transport/proxy configuration, mixed-fleet enforcement, and race/failure tests.

1. Apply the additive schema migration only. Its number is the next free migration at implementation time (0049 or later).
2. Deploy the new server binaries to every gateway instance with the deployment-wide feature flag OFF. Every credential-writing path in these binaries must set the transaction-local protocol marker, even with the flag OFF. Drain old binaries and connections; do not proceed until the fleet is converged. Old binaries cannot serve seats after the guard is installed because their writes fail closed.
3. Apply the separate protocol-guard trigger migration only after all gateways run the new binaries. The trigger now makes any old binary's protected credential write fail closed.
4. Enable the deployment-wide `SEAT_RESUME_TWO_PHASE_ENABLED` flag only after the trigger is installed. There is no supported mixed-fleet phase.
5. Enable in staging, then production; monitor pending expiry, activation CAS misses/unknown outcomes, takeover/deferred/aborted events, cap use, and host-approval recovery without logging credential material.
6. Rollback: turn the flag off and stop/drain all gateway instances so none is serving seats; safely inventory pending rows; while gateways remain stopped, drop the protocol trigger; then start/route only the fully converged rollback fleet. Never run old and new gateway binaries concurrently against the same seats. Migration down is unsupported after two-phase rows are used.

## Plain-language explanation for the owner (10 lines)

1. Today the server saves a new password before it knows whether the player received it.
2. If sending fails, the server tries to undo that save.
3. If undo also fails, the database can keep a password the player may never have seen.
4. A temporary safety list in one server process does not protect another process or a restart.
5. The fix is to save the new password as “waiting,” not as usable.
6. The player saves that waiting password before confirming receipt.
7. One database update then activates it and immediately retires the old password.
8. If confirmation is lost, the player sends both passwords in one reconnect message; only an active password works.
9. If anything fails before activation, only the old password works; the waiting one never does.
10. The shared database and its protocol guard make every server follow the same rule.

## Addendum: current-credential live-lease takeover

This addendum clarifies the lease policy for a reconnect that proves possession of the **current active credential**. Under the existing per-seat advisory lock, and only while the stored heartbeat satisfies the existing 15-second `socket_live` predicate, a request presenting that valid current credential may take over the live socket lease. The takeover displaces the prior socket and starts a normal credential rotation; the displaced client must reclaim the seat through host approval.

This exception applies only to proof of the current credential. The host-approved retry path does not displace a live lease, and any request without valid current-credential proof—including missing or invalid credentials—continues to be refused while the lease is live with close code 1008. Host-approval and other recovery eligibility rules otherwise remain unchanged.
